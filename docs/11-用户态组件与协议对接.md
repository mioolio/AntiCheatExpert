# 11 · 用户态组件逆向：清单、协议对接、方法

对象：`<ACE_ROOT>`（18 个 PE，合计约 90 MB）。
目标：搞清每个组件是什么、它们与已逆向的 `ACE-ADVT.sys` 协议如何对接、以及用什么方法继续深挖。

**结论 2**：`ACE-BASE.sys` 导入 **FLTMGR.SYS 16 个函数**，说明它注册为**文件系统微过滤器**——这是它能"看到所有文件访问"的结构性证据，而不是靠 Hook。

## 3. 用户态 ↔ 驱动 的协议对接（核心发现）

### 3.1 客户端在本地重建同一套记录

`ACE-CSI64.dll` 的 `.text` 里存在与驱动 `.data` 表格完全一致的记录构造：

```asm
0x180052315  mov  edx, 0x63AE442D        ; main 家族 base token (k=0)
0x18005231A  mov  r8d, 0x013500CA        ; 记录 magic
0x180052320  mov  rcx, rbp
0x180052323  call 0x180051C30            ; → thunk → .tvm0 (0x410535)
```

```asm
0x18004C9E4  mov  edx, 0x623782AD        ; aux 家族 token (k=2)
0x18004C9EE  mov  r8d, 0x013500CA        ; 同一个 magic
0x18004CA06  call 0x180051EA0            ; → thunk → .tvm0
```

两处 `magic` 完全相同 → 驱动 `.data 0x35020` 的那张 `{magic, flag, token}` 表**就是这套协议的注册表**，客户端与驱动共用同一套编号。

### 3.2 客户端命令清单（静态扫描结果）

扫描条件：`BA <imm32>` 后 12 字节内出现 `41 B8 CA 00 35 01`（`mov r8d, 0x013500CA`）。

| 家族 | 组件 | 使用的 k | 站点数 |
|---|---|---|---|
| main | `ACE-CSI64.dll` | 0（家族基址） | 1 |
| **aux** | `ACE-CSI64.dll` | **2, 4, 6, 7, 8, 10, 11, 12, 13, 17, 18, 22** | 12 |
| **aux** | `ACE-DFS64.dll` | **7, 18, 19** | 3 |

把这张表和 `docs/10`（aux = 缓冲区哈希）对照，含义就出来了：

- `ACE-CSI64.dll` 调用 12 条哈希子命令 → 它在**计算各类哈希/指纹**（进程内存、模块、自身）；
- `ACE-DFS64.dll` 只调 3 条（7、18、19） → 它是**文件哈希**（深度文件扫描，与 FLTMGR 侧联动）；
- main 家族只出现 k=0 → 客户端用它取"家族描述"，实际查询走的是 `docs/08` 那条状态通道。

### 3.3 记录构造器内部（`.tvm0` 0x410535）

追踪结果（`tools/trace_any.py`）：

```asm
0x410535  mov  rax, rsp
0x41053e  sub  rsp, 0x70
0x41056c  ... 保护器跳板 ...
0x4105a6  mov  esi, ebx                  ; 长度初值 0
0x4105b9  mov  esi, dword ptr [rdi]      ; 取调用方给的长度
0x4105c7  lea  eax, [rsi + 0x30]         ; ← 记录总长 = 数据 + 0x30
```

`+0x30`（48）与驱动回包结构 `{0x01343BEB, 0x30, status, ...}` 的 0x30 一致，说明**请求头与回包头共用同一个 48 字节布局**。

## 5. 结论汇总

1. 这是一套**统一打包、分层部署**的反作弊套件，内核侧三个驱动 + 一个微过滤器，用户态多个服务/UI/插件。
2. `ACE-BASE.sys` 是**文件系统微过滤器**（FLTMGR 16 导入），不是传统 SSDT Hook。
3. 用户态与内核共用**同一套 token/魔数协议**，`ACE-CSI64.dll` 是命令客户端，`ACE-DFS64.dll` 是文件哈希客户端。
4. `.tvm0` 保护器贯穿全部组件，**一套工具可覆盖全部**。
