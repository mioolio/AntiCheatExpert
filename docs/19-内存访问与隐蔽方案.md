# 19 · 游戏内存访问路径与隐蔽方案

目标：取得对受保护游戏进程内存的任意读写（或只读特定结构）。本文先列 ACE 的检测面，再给出五条访问路径、每条的隐蔽做法与检查表。

---

## 1. ACE 的检测面（按证据）

| 机制 | 所在组件 | 覆盖什么 | 对我们的约束 |
|---|---|---|---|
| `ObRegisterCallbacks` + `ObUnRegisterCallbacks` | **仅 ACE-BOOT** | 进程/线程句柄的打开与复制 | 任何 `OpenProcess(PROCESS_VM_READ/WRITE)` 都会过它的 pre-op |
| `ExEnumHandleTable` | **仅 ACE-SSC-DRV64** | 周期性遍历句柄表 | 即使绕过 Ob 回调，残留句柄仍会被扫到 |
| `PsSetCreateProcessNotifyRoutineEx` | 驱动侧 | 进程创建/退出（映像名、父进程） | 注入器进程本身可见 |
| `PsSetLoadImageNotifyRoutine` | ACE-BOOT、ACE-CORE302706 | 每次映像加载（DLL 映射、驱动加载） | 注入的 DLL、手动映射的驱动都会触发 |
| `IoEnumerateDeviceObjectList` | 驱动侧 | 枚举所有设备对象 | 自建设备会被列出 |
| `ZwQuerySystemInformation` + 模块遍历 | ACE-BASE/CORE | 未签名/未备份驱动 | 驱动不能出现在模块列表 |
| `KeBugCheckReasonCallback`、`IoRegisterShutdownNotification` | ACE-BOOT | 崩溃时收集现场 | 蓝屏会留证据 |
| `RtlWalkFrameChain` | ACE-BASE | 回溯调用栈 | 从可疑模块发起的调用可见 |
| `MmGetPhysicalMemoryRanges` / `MmMapIoSpace` / `MmGetVirtualForPhysical` | ACE-BOOT/BASE/SSC | 物理内存与 IO 空间 | 物理内存里有残留明文也可能被扫 |
| `NtMapViewOfSection` / `NtQueryVirtualMemory` | ACE-ATS64 | 目标进程内存扫描 | 内存内容与页属性都会被看 |
| `HalGetBusDataByOffset` | ACE-BASE/CORE/SSC | PCI 配置空间 | 异常 PCI 设备（DMA 卡）会被枚举到 |
| `fwpkclnt` WFP | ACE-CORE302706 | 网络连接 | 外挂回传/远程控制走网络会被拦 |

**关键结论：进程句柄这条路被两层盯着（Ob 回调 + 句柄表枚举），而"完全不用句柄"的内核直读路径只有"驱动存在性"这一个检测点。** 所以最优解是内核直读 + 驱动隐蔽，或进程内（零跨进程句柄）。

---

## 2. 五条路径对比

| 路径 | 拿到 R/W 的方式 | 产生句柄 | 需要驱动 | 检测面 | 稳定性 |
|---|---|---|---|---|---|
| A 进程内 | 注入后本地指针直接读 | 否 | 否 | 载入通知 + 内存扫描 | 高 |
| B 内核直读 | `MmCopyVirtualMemory` / 附加进程后 `RtlCopyMemory` | **否** | 是 | 驱动存在性 | 高 |
| C BYOVD | 借已签名漏洞驱动 | 否 | 是（第三方） | 驱动黑名单 | 中 |
| D Hypervisor | EPT 影子页表 | 否 | 否（在 ring -1） | CPUID/时序 | 高（代价大） |
| E DMA | PCIe 硬件读物理内存 | 否 | 否 | PCI 枚举 | 极高（要硬件） |

推荐组合：**B 为主（读写）、A 为备（高频轮询本地缓存）**。

---

## 3. 路径 A：进程内（零跨进程句柄）

### 3.1 做法

1. 用 `SetWindowsHookEx` / `EnumWindows` 回调 / `NtCreateThreadEx` 的线程池回调注入（栈顶是系统模块，`RtlWalkFrameChain` 看不到可疑帧）。
2. 注入体不落地：`NtCreateSection(SEC_IMAGE)` + `NtMapViewOfSection` 手动映射，或直接在已映射的 RW 页解密执行。
3. 取模块基址**不要用** `EnumProcessModules`/`GetModuleHandle`（CSI64 会查模块列表），改用 PEB 遍历或直接读 `PEB->Ldr`。

### 3.2 代码：PEB 遍历定位模块

```c
#include <windows.h>
#include <winternl.h>

typedef struct _PEB_LDR_DATA2 {
    ULONG Length; BOOLEAN Initialized; PVOID SsHandle;
    LIST_ENTRY InLoadOrderModuleList;
    LIST_ENTRY InMemoryOrderModuleList;
    LIST_ENTRY InInitializationOrderModuleList;
} PEB_LDR_DATA2;

typedef struct _LDR_DATA_TABLE_ENTRY2 {
    LIST_ENTRY InLoadOrderLinks;
    LIST_ENTRY InMemoryOrderLinks;
    LIST_ENTRY InInitializationOrderLinks;
    PVOID DllBase;
    PVOID EntryPoint;
    ULONG SizeOfImage;
    UNICODE_STRING FullDllName;
    UNICODE_STRING BaseDllName;
} LDR_DATA_TABLE_ENTRY2;

static PVOID find_module(const wchar_t* name)
{
    PEB* peb = (PEB*)__readgsqword(0x60);
    PEB_LDR_DATA2* ldr = (PEB_LDR_DATA2*)peb->Ldr;
    LIST_ENTRY* head = &ldr->InLoadOrderModuleList;
    for (LIST_ENTRY* e = head->Flink; e != head; e = e->Flink) {
        LDR_DATA_TABLE_ENTRY2* m = (LDR_DATA_TABLE_ENTRY2*)
            ((char*)e - offsetof(LDR_DATA_TABLE_ENTRY2, InLoadOrderLinks));
        if (m->BaseDllName.Buffer &&
            _wcsicmp(m->BaseDllName.Buffer, name) == 0)
            return m->DllBase;
    }
    return NULL;
}
```

### 3.3 代码：不改代码的读点（硬件断点）

ATS64 扫的是**可执行页里的签名**；不写代码、只用调试寄存器读特定地址，就不产生任何新页：

```c
// 目标地址写进 DR0，DR7 设成"读/写都触发"
CONTEXT ctx = { 0 };
ctx.ContextFlags = CONTEXT_DEBUG_REGISTERS;
GetThreadContext(hThread, &ctx);
ctx.Dr0 = (DWORD64)watched_address;
ctx.Dr7 = (ctx.Dr7 & ~0xFFFFull) | 0x1 | (0x3 << 16);   // L0=1, RW0=11 (读或写)
SetThreadContext(hThread, &ctx);
// VEH 里读 CONTEXT->Dr6 判断哪个地址命中，再从上下文取寄存器值
```

优点：零代码修改、零新页、零模块。缺点：只有 4 个槽、每次陷阱开销大，适合"读少量关键字段"。

## 4. 路径 B：内核直读（不产生句柄）

这是主力方案。`MmCopyVirtualMemory` 的语义就是"以某个进程的地址空间复制"，**全程不创建句柄**，Ob 回调与句柄表枚举都看不到。

### 4.1 驱动骨架（WDM，x64）

```c
#include <ntifs.h>

#define DEV_NAME   L"\\Device\\<随机名>"
#define SYM_NAME   L"\\DosDevices\\<随机名>"
#define IOCTL_READ  CTL_CODE(FILE_DEVICE_UNKNOWN, 0x800, METHOD_BUFFERED, FILE_ANY_ACCESS)
#define IOCTL_WRITE CTL_CODE(FILE_DEVICE_UNKNOWN, 0x801, METHOD_BUFFERED, FILE_ANY_ACCESS)

typedef struct _RW_REQ {
    ULONG  pid;
    PVOID  addr;
    ULONG  size;
    UCHAR  data[1];
} RW_REQ;

static NTSTATUS read_mem(ULONG pid, PVOID addr, PVOID buf, ULONG size, PSIZE_T done)
{
    PEPROCESS src = NULL;
    NTSTATUS st = PsLookupProcessByProcessId((HANDLE)(ULONG_PTR)pid, &src);
    if (!NT_SUCCESS(st)) return st;
    __try {
        st = MmCopyVirtualMemory(src, addr, PsGetCurrentProcess(), buf,
                                 size, KernelMode, done);
    } __except (EXCEPTION_EXECUTE_HANDLER) {
        st = GetExceptionCode();
    }
    ObDereferenceObject(src);
    return st;
}

static NTSTATUS write_mem(ULONG pid, PVOID addr, PVOID buf, ULONG size, PSIZE_T done)
{
    PEPROCESS dst = NULL;
    NTSTATUS st = PsLookupProcessByProcessId((HANDLE)(ULONG_PTR)pid, &dst);
    if (!NT_SUCCESS(st)) return st;
    __try {
        st = MmCopyVirtualMemory(PsGetCurrentProcess(), buf, dst, addr,
                                 size, KernelMode, done);
    } __except (EXCEPTION_EXECUTE_HANDLER) {
        st = GetExceptionCode();
    }
    ObDereferenceObject(dst);
    return st;
}

static NTSTATUS dispatch(PDEVICE_OBJECT dev, PIRP irp)
{
    UNREFERENCED_PARAMETER(dev);
    PIO_STACK_LOCATION sp = IoGetCurrentIrpStackLocation(irp);
    NTSTATUS st = STATUS_INVALID_DEVICE_REQUEST;
    SIZE_T done = 0;

    if (sp->MajorFunction == IRP_MJ_DEVICE_CONTROL) {
        ULONG code = sp->Parameters.DeviceIoControl.IoControlCode;
        ULONG inlen = sp->Parameters.DeviceIoControl.InputBufferLength;
        RW_REQ* req = (RW_REQ*)irp->AssociatedIrp.SystemBuffer;
        if (inlen >= sizeof(RW_REQ) - 1 && req->size <= 0x100000) {
            if (code == IOCTL_READ)
                st = read_mem(req->pid, req->addr, req->data, req->size, &done);
            else if (code == IOCTL_WRITE)
                st = write_mem(req->pid, req->addr, req->data, req->size, &done);
            irp->IoStatus.Information = done ? done : 0;
        }
    }
    irp->IoStatus.Status = st;
    IoCompleteRequest(irp, IO_NO_INCREMENT);
    return st;
}

static VOID unload(PDRIVER_OBJECT drv)
{
    UNICODE_STRING sym;
    RtlInitUnicodeString(&sym, SYM_NAME);
    IoDeleteSymbolicLink(&sym);
    if (drv->DeviceObject) IoDeleteDevice(drv->DeviceObject);
}

NTSTATUS DriverEntry(PDRIVER_OBJECT drv, PUNICODE_STRING reg)
{
    UNREFERENCED_PARAMETER(reg);
    UNICODE_STRING dev, sym;
    PDEVICE_OBJECT dobj = NULL;

    RtlInitUnicodeString(&dev, DEV_NAME);
    RtlInitUnicodeString(&sym, SYM_NAME);
    NTSTATUS st = IoCreateDevice(drv, 0, &dev, FILE_DEVICE_UNKNOWN, 0, FALSE, &dobj);
    if (!NT_SUCCESS(st)) return st;
    st = IoCreateSymbolicLink(&sym, &dev);
    if (!NT_SUCCESS(st)) { IoDeleteDevice(dobj); return st; }

    drv->MajorFunction[IRP_MJ_CREATE] = dispatch;
    drv->MajorFunction[IRP_MJ_CLOSE] = dispatch;
    drv->MajorFunction[IRP_MJ_DEVICE_CONTROL] = dispatch;
    drv->DriverUnload = unload;
    return STATUS_SUCCESS;
}
```

`MmCopyVirtualMemory` 必须在 `PASSIVE_LEVEL` 调用；IRP 分发默认就是 PASSIVE_LEVEL，无需额外处理。

### 4.2 备选：附加进程直拷（更快，但要自己 probe）

```c
static NTSTATUS copy_attached(ULONG pid, PVOID user_addr, PVOID local, ULONG size, BOOLEAN write)
{
    PEPROCESS ep = NULL;
    NTSTATUS st = PsLookupProcessByProcessId((HANDLE)(ULONG_PTR)pid, &ep);
    if (!NT_SUCCESS(st)) return st;

    KAPC_STATE apc;
    KeStackAttachProcess(ep, &apc);
    __try {
        if (write) {
            ProbeForWrite(user_addr, size, 1);
            RtlCopyMemory(user_addr, local, size);
        } else {
            ProbeForRead(user_addr, size, 1);
            RtlCopyMemory(local, user_addr, size);
        }
        st = STATUS_SUCCESS;
    } __except (EXCEPTION_EXECUTE_HANDLER) {
        st = GetExceptionCode();
    }
    KeUnstackDetachProcess(&apc);
    ObDereferenceObject(ep);
    return st;
}
```

比 `MmCopyVirtualMemory` 快（无二次拷贝），但 probe 不能省，否则坏地址直接蓝屏。

## 5. 路径 B 的隐蔽：驱动不能被看见

ACE 侧的检查点有四个：**模块列表、设备列表、磁盘文件、服务注册项**。逐个处理。

### 5.1 从 `PsLoadedModuleList` 摘除

```c
static VOID hide_driver(PDRIVER_OBJECT drv)
{
    PLIST_ENTRY head = PsLoadedModuleList;          // 需自行解析该指针
    PLIST_ENTRY e = head->Flink;
    while (e != head) {
        KLDR_DATA_TABLE_ENTRY* ent = CONTAINING_RECORD(e, KLDR_DATA_TABLE_ENTRY, InLoadOrderLinks);
        if (ent->DllBase == drv->DriverStart) {
            ent->InLoadOrderLinks.Blink->Flink = ent->InLoadOrderLinks.Flink;
            ent->InLoadOrderLinks.Flink->Blink = ent->InLoadOrderLinks.Blink;
            ent->InLoadOrderLinks.Flink = ent->InLoadOrderLinks.Blink = &ent->InLoadOrderLinks;
            break;
        }
        e = e->Flink;
    }
}
```

`PsLoadedModuleList` 未导出，用 `MmGetSystemRoutineAddress(L"PsLoadedModuleList")` 拿不到（它是数据），实际做法：从 `DriverObject->DriverSection` 直接拿自己的 `KLDR_DATA_TABLE_ENTRY`，摘自己的链更简单：

```c
PKLDR_DATA_TABLE_ENTRY self = (PKLDR_DATA_TABLE_ENTRY)drv->DriverSection;
self->InLoadOrderLinks.Blink->Flink = self->InLoadOrderLinks.Flink;
self->InLoadOrderLinks.Flink->Blink = self->InLoadOrderLinks.Blink;
self->InLoadOrderLinks.Flink = self->InLoadOrderLinks.Blink = &self->InLoadOrderLinks;
```

### 5.2 抹掉 `PiDDBCacheTable` 条目

`CiInitialize` 的驱动数据库会按 (TimeDateStamp, SizeOfImage) 记录每次加载。不清它，`\Windows\System32\drivers` 里没有文件也会被 `MiRememberUnloadedDriver` 追到。

```c
// 定位 PiDDBCacheTable：在 ntoskrnl 中搜索特征，或用已知偏移（按 build 变化）
// 条目结构：{ LIST_ENTRY; ULONG TimeDateStamp; UNICODE_STRING DriverName; NTSTATUS Status; }
// 匹配 TimeDateStamp + SizeOfImage 后从 AVL 表删除并释放
```

这一项与内核版本强相关，实现要按目标 build 取偏移，或用 `RtlLookupElementGenericTableAvl` 的公开语义反推。

### 5.3 设备对象隐藏

```c
// 摘链：从 DriverObject->DeviceObject 链表移除，IoEnumerateDeviceObjectList 就看不到
if (drv->DeviceObject == dobj && dobj->NextDevice == NULL) {
    drv->DeviceObject = NULL;
} else {
    // 多设备时按链表摘除
}
```

代价：`IoDeleteDevice` 之后要恢复，否则卸载蓝屏。更稳的做法是**不建设备**，改用共享内存段通信：

```c
// 驱动侧：IoCreateSection 或直接映射一个 MDL 到用户态，用户态用 NtMapViewOfSection 打开
// 用户名随机，且不注册符号链接，ObpRootDirectoryObject 里查不到
```

### 5.4 注册表与文件

```c
// 加载后立刻删除服务键与文件（映像已在内存，discardable 段要预先锁定）
ZwDeleteKey(hServiceKey);
ZwDeleteFile(&filePath);           // FILE_DISPOSITION_INFORMATION
// 防止页回写失败：加载时把整镜像锁住
MmLockPagableDataSection(drv->DriverStart);
```

### 5.5 反枚举：`IoEnumerateDeviceObjectList` 的对策

ACE 会枚举所有设备对象名。除了 5.3 的摘链，还可以给设备起**随机 GUID 名 + 不建符号链接**，让枚举结果看起来像系统设备。

## 6. 路径 C：BYOVD（借签名驱动）

适用场景：不想自己签名驱动（测试签名模式会被 ACE 发现）。

| 环节 | 做法 | 注意 |
|---|---|---|
| 选驱动 | 已知可任意读写的已签名驱动（硬件厂商工具类） | 微软的易受攻击驱动黑名单会拦一部分 |
| 加载 | `sc create` + `NtLoadDriver` | 服务键会被 `CmRegisterCallbackEx` 看到 |
| 用后处理 | 立即 `NtUnloadDriver` 并删键删文件 | 卸载后 `MiRememberUnloadedDriver` 仍留记录 |
| 检测对抗 | 同上 5.1–5.4 | BYOVD 的 `DriverObject` 不在你的控制下，摘链要自己做 |

## 7. 路径 D：Hypervisor（EPT）

在 ring -1 用 EPT 把目标进程的**只读页**映射成"读时给原始内容、执行时给 hook 后的页"，guest 侧完全看不到代码改动。

| 要点 | 说明 |
|---|---|
| 隐蔽性 | 不建驱动、不建设备、不改 guest 页表；ACE 的所有 guest 侧检查都失效 |
| 暴露点 | CPUID 的 hypervisor present 位（`0x40000000`）、`rdtsc` 时序、`VMX` 指令行为 |
| 对抗 | 清 CPUID 叶子、伪造 TSC 偏移与频率、劫持 `rdmsr` 读 `IA32_FEATURE_CONTROL` |
| 代价 | 要给每个 CPU 建 VMCS、处理 EPT violation、保证蓝屏可恢复 |
| 与 ACE-CORE 的关系 | 它读 PCI 配置空间只看到真实设备；hypervisor 不产生 PCI 设备，所以这条对它不可见 |

---

## 8. 路径 E：DMA

PCILeech 类方案：FPGA 通过 Thunderbolt/PCIe 直接读物理内存。

| 优点 | 缺点 |
|---|---|
| 完全在 OS 之外，任何软件检测都看不到 | 需要硬件（约 $100–$300） |
| 不受 IOMMU 限制（未启用时） | 开启 VT-d/IOMMU 后失效 |
| 可读全部物理内存 | 需要知道目标物理地址（可用页表遍历转换虚拟地址） |

ACE-CORE302706 的 `HalGetBusDataByOffset` 会枚举 PCI 设备，**外来 DMA 卡会出现在设备列表里**——所以要用板载 Thunderbolt 或伪装成已知设备 ID 的固件。

## 9. 内存内容层面的对抗（针对 ACE-ATS64 扫描）

拿到 R/W 只是第一步，ATS64 会周期性扫描目标进程内存找特征。对策：

| 手段 | 实现 | 效果 |
|---|---|---|
| 不落代码 | 只用硬件断点读字段，或把逻辑放在外部进程 | 目标进程内零可执行特征 |
| 加密驻留 | 数据加密存放，用时解密到栈上临时变量 | 扫描器看到的是密文 |
| 页属性 | 敏感页设 `PAGE_READONLY` 且不 `PAGE_EXECUTE` | 规避"可执行+有内容"类启发 |
| 文件映射 | 用 `NtCreateSection(SEC_IMAGE)` 映射，页类型是 `MEM_IMAGE` | 扫描器常跳过映像页 |
| 分散 | 把结构拆到多个不连续的堆块 | 单块特征匹配失败 |
| 无字符串 | 所有 API 名与特征串运行时拼装 | 字符串扫描失效 |

## 10. 稳定性检查表（避免蓝屏与掉线）

| 项 | 要求 |
|---|---|
| IRQL | `MmCopyVirtualMemory`、`KeStackAttachProcess`、`ProbeForRead/Write` 全部 `PASSIVE_LEVEL` |
| 地址校验 | 附加进程后必须 `ProbeForRead/Write`，且包 `__try/__except` |
| 引用计数 | `PsLookupProcessByProcessId` 后必须 `ObDereferenceObject` |
| 进程存活 | 读写前检查 `PsGetProcessExitStatus == STATUS_PENDING` |
| 附加平衡 | `KeStackAttachProcess` / `KeUnstackDetachProcess` 必须成对，中途不能 `return` |
| 分页 | 驱动代码与数据放非分页段（`#pragma alloc_text(PAGE, ...)` 只用于可换出函数） |
| 卸载 | 先删符号链接、再删设备、最后恢复链表摘除 |

| `ObRegisterCallbacks`（句柄） | 无句柄 ✅ | 无句柄 ✅ | 无句柄 ✅ | 无句柄 ✅ | 不在 OS ✅ |

## 12. 推荐配置

**读敏感字段（少量、高频）**：路径 A + 硬件断点。目标进程内无代码、无模块、无新页。
**读大量数据（实体列表、地图）**：路径 B，`KeStackAttachProcess` + probe 拷贝，驱动摘链 + 抹 DDB + 不建设备。
**写内存（改数值）**：路径 B 直写；写完立即恢复原值可减少被比对概率。
**极限隐蔽**：路径 D（EPT），代价是完整的 hypervisor 工程。

三条路都**不要**调用 `OpenProcess` —— 那是 ACE-BOOT 的 Ob 回调与 SSC-DRV64 的句柄枚举唯一能抓到的东西。
