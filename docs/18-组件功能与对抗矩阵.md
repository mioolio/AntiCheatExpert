# 18 · 组件功能详解、拦截点与绕过方法

对象：`AntiCheatExpert` 套件 18 个组件（`ACE-ADVT.sys` 见独立仓库 mioolio/ACE-ADVT）。

每个组件按三段写：**干什么**（证据落在导入表与字符串上）、**拦截点**（具体 API / 回调 / 设备 / 注册项）、**绕过方法**（可操作，附验证方式）。
凡属推断而非直接证据的，标注「推断」。

## 0. 总览矩阵

| 组件 | 类型 | 运行位置 | 主要手段 | 主要弱点 |
|---|---|---|---|---|
| `ACE-BOOT.sys` | 驱动 | boot-start（`Start=1`） | 注册表回调、裸磁盘读取、物理内存 | 注册表回调可被撤销；分区直接读可被过滤 |

| `ACE-ATS64.dll` | 用户态 | 注入进程 | 内存扫描（`NtQueryVirtualMemory`/`NtMapViewOfSection`）、WinHTTP | 扫描依赖 API，可被 hook |

| `SGuardUpdate64.exe` | 服务 | LocalSystem | `CryptSignHashW` 更新包验签、同 GUID 互斥体 | 更新源可被劫持（需证书） |
| `Uninstaller.exe` / `Uninstall64.exe` | 工具 | 用户 | 停服务、删注册项、`SendMessageW` 通知 | 只做卸载，无防护价值 |

# 一、内核驱动

## 1. `ACE-BOOT.sys`

### 1.1 干什么

| 证据 | 含义 |
|---|---|
| `CmRegisterCallbackEx` / `CmUnRegisterCallback` / `CmCallbackGetKeyObjectID` | 注册**注册表操作回调**，拦截注册表读写 |
| `\Device\Harddisk%d\Partition0`、`\Device\HarddiskVolume` | 直接打开**裸磁盘/分区**，绕过文件系统 |
| `\device\physicalmemory` | 尝试映射物理内存 |
| `\Registry\Machine\SYSTEM\ControlSet%.3u\services\` | 按 ControlSet 枚举服务项（持久化自查） |
| `SOFTWARE\Microsoft\Windows\Dwm` | 关注 DWM 键（窗口/合成相关，常用于检测注入/覆盖层） |
| `ExCreateCallback` / `ExRegisterCallback` | 内核回调对象，用于跨驱动通知 |
| `\Device\ACE-BOOT` + `\DosDevices\Global\ACE-BOOT` | 暴露控制设备 |
| 日志子系统（文件名 `ace-boot-%04d%02d%02d-%02d%02d%02d.log`，魔数 `0x013525DD`，记录加密） | 全量记录启动期事件 |

定位：boot-start 驱动，在文件系统栈就绪前用**直接磁盘访问**做完整性检查，注册表回调做持久化监控，日志记录一切。

### 1.2 拦截点

| 拦截点 | 位置 | 触发 |
|---|---|---|
| 注册表写/删 | `CmRegisterCallbackEx` 回调 | 任何受监控键的 `RegNtPreSetValueKey` 等 |
| 裸磁盘读 | `\Device\Harddisk%d\Partition0` | 周期性（推断：校验引导区/驱动文件） |
| 日志写 | `\SystemRoot\ace-boot-*.log` | 每次事件 |

### 1.3 绕过方法

| 目标 | 方法 | 验证 |
|---|---|---|
| 改注册表不被记录 | 用 `NtSetValueKey` 的**事务**（`RegCreateKeyTransacted`）——回调仍会触发，但可用 `RegNotifyChangeKeyValue` 之外的路径：直接在 **hive 文件**上改（卸载后） | 改完重挂 hive 看日志有无对应条目 |
| 绕过裸磁盘校验 | 校验读的是 `Partition0` 的**前若干扇区** → 把改动放在分区**尾部**或 `$LogFile` 区域之外的未分配簇 | 修改后重启，看日志是否报完整性失败 |
| 让文件校验读到旧内容 | 校验用 `FltGetFileNameInformationUnsafe` 拿到的路径与实际读取路径可能不一致 → 用**硬链接/挂载点**让路径解析与实际卷不同 | 用 `fsutil hardlink` 建同名指向，比对校验结果 |
| 停掉日志 | 日志文件被 `ACE-BOOT` 独占？实测可写 → 用 `FILE_SHARE_READ` 打开并截断会失败；改为**改名**（`MoveFileEx` 带 `MOVEFILE_REPLACE_EXISTING` 需权限） | 改名成功说明无独占保护 |
| 卸载驱动 | `Start=1` 且由 `ACE-Service` 守护 → 先停 `AntiCheatExpert Protection` 再 `sc stop ACE-BOOT`（会蓝屏，因 boot 驱动不支持停止） | 静态分析确认无 `IRP_MJ_SHUTDOWN` 处理 |

> 关键结论：`ACE-BOOT` 的强项是**启动早期**（其它驱动还没起来时它已经在读盘），弱项是**运行期**——它的注册表回调与文件校验都可被上层过滤或路径混淆影响。

## 2. `ACE-BASE.sys`

### 2.1 干什么

| 证据 | 含义 |
|---|---|
| `FLTMGR.SYS` 导入 16 个：`FltGetFileNameInformationUnsafe`、`FltReleaseFileNameInformation` 等 | **只做文件信息查询**，未注册 minifilter（`FltRegisterFilter` 从未调用）——文件拦截靠别人，它负责"拿到路径" |
| `NDIS.SYS`(3) + `HIDPARSE.SYS`(1) | 网络与 HID 设备层的挂接 |
| `IoCreateDeviceSecure` + `SeConvertStringSecurityDescriptorToSecurityDescriptor`（字符串表） | 用 SDDL 建**安全设备**，按 IOCTL 校验访问权限 |
| 设备名 `\Device\{TF9AC12E-S60X-E25G-N67G-IC8A82086DAN}`（混淆 GUID） | 设备名不可预测，防止按名字打开 |
| `\\.\ACE-BASE` | 同时暴露一个**易读别名**（互补） |
| `\device\physicalmemory` | 物理内存访问 |
| `ExAcquireRundownProtection` / `ExEventObjectType` / `ExSemaphoreObjectType` | 对象类型判定 → **检测句柄是否指向进程/线程对象** |
| `ExGetPreviousMode` | 区分请求来自用户态还是内核态 |
| `expand 32-byte k`（字符串表） | ChaCha 系列流密码（通信加密） |

### 2.2 拦截点

| 拦截点 | 机制 |
|---|---|
| 进程/线程句柄 | 通过对象类型判断 + 句柄权限，识别 `PROCESS_VM_READ` 类打开 |
| 文件路径 | `FltGetFileNameInformationUnsafe` 拿最终路径（不做过滤，只观察） |
| 设备访问 | SDDL DACL + `IoValidateDeviceIoControlAccess` 逐 IOCTL 校验 |
| 物理内存 | `\device\physicalmemory` 映射后扫描 |
| 栈完整性 | 栈 cookie（`__security_cookie`）校验，检测返回地址篡改 |

### 2.3 绕过方法

| 目标 | 方法 | 说明 |
|---|---|---|
| 打开设备 | 设备名是混淆 GUID，但可用 `NtOpenDirectoryObject` 枚举 `\Device` 找到；或直接用 `\\.\ACE-BASE` 别名（受 DACL 限制） | 枚举 `\Device` 目录对象即可拿到真实名字 |
| 绕过句柄检测 | 检测依据是"句柄存在 + 对象类型 + 授予权限" → 用**内核回调已建立后**再打开、或用 `NtDuplicateObject` 从已有句柄派生（不产生新的 open 记录） | 需已有高权限句柄 |
| 绕过物理内存扫描 | 扫描依赖 `\device\physicalmemory` 映射 → 若 `SeLockMemoryPrivilege` 被撤销则失败；或让目标页处于 **pagefile/standby**（`SetProcessWorkingSetSize` + `EmptyWorkingSet`） | 扫描窗口内把关键页换出 |
| 绕过 FLTMGR 路径观察 | 用 `\\.\C:` 卷句柄 + 相对偏移直接 I/O（不经文件对象路径解析），观察者拿到的名字是卷设备 | 需管理员 |
| 绕过栈校验 | 栈 cookie 只在函数返回时校验 → 覆盖**未使用 cookie 的叶子函数**的返回地址，或改 IAT/GOT 而非返回地址 | 静态扫描每个函数的 `__security_check_cookie` 调用 |
| 通信解密 | ChaCha 需要 key/nonce → key 在 `.tvm0`（0x2E8000 字节）内派生 | 见 docs/12 |

> `ACE-BASE` 是整套的**基座**：它不自己拦截文件，而是给上层（`ACE-CORE`/`ACE-CSI64`）提供"路径、句柄、内存"三类事实。打掉它的设备就等于让上层瞎掉——但设备名混淆 + SDDL 使这条路成本很高。

## 3. `ACE-CORE302706.sys`

### 3.1 干什么

| 证据 | 含义 |
|---|---|
| `fwpkclnt.sys`(10) | **WFP 过滤器**：在 `FWPM_LAYER_ALE_*` 层拦截连接/收发 |
| `NDIS.SYS`(3) + `NETIO.SYS`(1) | 网络栈底层挂接 |
| `HalGetBusDataByOffset` / `HalSetBusDataByOffset` | **PCI 配置空间读写** → 枚举/识别硬件（GPU、网卡），也能改设备配置 |
| `HalDispatchTable` | 引用 HAL 派发表（常用于 hook 或检测被 hook） |
| `FltGetFileNameInformationUnsafe` | 文件路径观察（同 ACE-BASE） |
| `.data` 预留约 90 MB BSS | 大范围内存扫描缓冲 |
| `IoAllocateIrp` | 自建 IRP，绕过过滤驱动直接下发 |

### 3.2 拦截点

| 拦截点 | 机制 |
|---|---|
| 网络连接 | WFP `ALE_AUTH_CONNECT` / `ALE_AUTH_RECV_ACCEPT` 层，可按进程/端口放行或阻断 |
| 网络数据 | `FWPM_LAYER_STREAM_V4/V6` 层（推断：按导入集合判断） |
| PCI 设备 | 配置空间读写，读 VendorID/DeviceID 判定是否虚拟机/可疑设备 |
| 文件 | 路径观察 |

### 3.3 绕过方法

| 目标 | 方法 | 说明 |
|---|---|---|
| 绕过 WFP 连接拦截 | WFP 是**分层**的：注册一个 `weight` 更高（`FWP_ACTION_PERMIT` 且 `weight = 0xFFFFFFFF`）的过滤器即可覆盖；或直接用 **RAW socket / NDIS 协议驱动**绕过 WFP（WFP 在 TCP/IP 栈内，RAW 也经过，但 `FWPM_LAYER_ALE_*` 对 raw 的连接判定不同） | 需管理员，且会被 `ACE-BASE` 的驱动列表检查发现 |
| 绕过 PCI 检测 | 检测读的是配置空间 `0x00`（Vendor/Device）与 `0x2C`（Subsystem）→ 在 **hypervisor 层**伪造（VMware 的 `hypervisor.cpuid.v0 = FALSE` + 自定义 DMI/PCI ID） | 需控制宿主 |
| 绕过大内存扫描 | 90 MB BSS 说明是**滑动窗口**扫描 → 让目标内存大部分时间不可读（`PAGE_NOACCESS` + `VEH` 按需解密），扫描命中率降到噪声 | 典型 packer 手法 |
| 绕过 IoAllocateIrp 直发 | 自建 IRP 会经过**所有**过滤驱动（包括它自己）→ 无法用它绕过自身；反而可利用：在 `IRP_MJ_DEVICE_CONTROL` 上挂过滤，观察它下发了什么 | — |

## 4. `ACE-SSC-DRV64.sys`

### 4.1 干什么

| 证据 | 含义 |
|---|---|
| `ExEnumHandleTable` | **枚举全系统句柄表** → 找"谁打开了我的进程/文件" |
| `IoBuildSynchronousFsdRequest` / `IoBuildDeviceIoControlRequest` | 自建同步 I/O，直接对文件系统设备下发（不经高层路径解析） |
| `\Device\PhysicalMemory`（注意大小写） | 物理内存 |
| `HalGetBusDataByOffset` / `HalSetBusDataByOffset` | PCI 配置空间 |
| `IoCreateDevice` + 符号链接 `\DosDevices\ACE-SSC-DRV64` | 自己的控制设备（名字**未混淆**） |
| 注册表 `Services\ACE-SSC-DRV64` | 自注册服务 |
| `.tvm0`? 无（该驱动无保护段，1.5 MB 全明文） | 分析成本最低的一个驱动 |

### 4.2 拦截点

| 拦截点 | 机制 |
|---|---|
| 句柄使用 | 枚举句柄表，按对象类型 + 授予权限匹配"可疑的跨进程访问" |
| 文件读取 | 直接构造 FSD 请求读文件（绕过 Win32 层） |
| 物理内存 | 直接映射 |

### 4.3 绕过方法

| 目标 | 方法 | 说明 |
|---|---|---|
| 避开句柄枚举 | 枚举有**竞态窗口**：句柄在 `ObpCreateHandle` 之后才进表，`ExEnumHandleTable` 遍历时可能漏掉短生命周期句柄 → 用完立刻 `CloseHandle` | 实测可把存活时间压到微秒级 |
| 让枚举结果失真 | 枚举回调里按 `ObjectType` 比对；用 **`NtDuplicateObject` 产生同类型新句柄**不会改变"谁打开"的判定依据（仍指向同一对象）→ 真正有效的是用**内核态直接读**（`MmCopyVirtualMemory`）不产生句柄 | 需驱动 |
| 绕开 FSD 直读 | 它读的是文件**内容**，不看路径 → 把敏感内容放到**备用数据流（ADS）** 或 `$MFT` 之外的元数据区 | 需 NTFS 权限 |
| 关闭设备 | 设备名未混淆 → `\\.\ACE-SSC-DRV64` 可直接打开；DACL 若宽松则可发 IOCTL 关闭其监控 | 用 `WinObj` 看 SDDL |

> 这个驱动是**整套里最容易打的一个**：无保护段、设备名未混淆、明文导入表。优先从这里建立"驱动 ↔ 用户态"的协议理解。

# 二、用户态组件

## 6. `ACE-CSI64.dll`

### 6.1 干什么

| 证据 | 含义 |
|---|---|
| `\Device\FileInfo` | 向某驱动查询**文件信息**（谁在访问、是否被改） |
| `\\.\0:` | 直接卷访问 |
| `SYSTEM\ControlSet001\Services\bam\State\UserSettings\` | 读 **BAM**（Background Activity Moderator）——系统记录的"哪个程序被谁执行过" |
| `NtQueryInformationProcess` / `NtQueryInformationThread` / `NtQueryVirtualMemory` / `NtQuerySystemInformation` | 进程、线程、内存、系统信息全查 |
| `CryptQueryObject` / `CryptMsgGetParam` | 验证嵌入签名 |
| `WTSAPI32`(3) | 会话枚举 |

### 6.2 拦截点 / 6.3 绕过

| 目标 | 方法 |
|---|---|
| 隐藏进程 | 它按 `NtQuerySystemInformation(SystemProcessInformation)` 枚举 → hook 该函数的**返回缓冲**（不是函数本身），过滤掉目标项；或让目标进程以 `PPL`/`System` 身份运行（枚举可见但查询受限） |
| 抹掉执行痕迹 | BAM 键在 `Services\bam\State\UserSettings\{SID}\` 下，按可执行文件路径记录 → 删除对应值即可（服务停止后） |
| 绕过内存查询 | `NtQueryVirtualMemory` 对 `PAGE_NOACCESS` 区域返回 `STATUS_ACCESS_DENIED`，扫描器会跳过 → 用 guard page + VEH |
| 阻止它查文件信息 | `\Device\FileInfo` 是设备 IOCTL，名字明文可见 → 用 `WinObj` 找 SDDL，或用 minifilter 过滤其 IRP |

## 7. `ACE-DFS64.dll`

### 7.1 干什么

| 证据 | 含义 |
|---|---|
| `\\.\DISPLAY`、`\\.\C:`、`SOFTWARE\Microsoft\DirectX` | 显示器 + 磁盘 + DirectX 信息 → **硬件指纹** |
| `SendARP`（`IPHLPAPI`） | 取 MAC 地址（局域网 ARP） |
| `CryptGenKey` / `CryptExportKey` / `CryptSignHashW` / `CryptSetProvParam` | RSA 密钥生成、导出、签名（设备身份） |
| `WinHTTP`(10) | 上报 |
| `SetEntriesInAclW` / `SetFileAttributesW` | 文件保护 |
| 23 MB 体积 + `.tvm0` | 主扫描引擎之一 |

### 7.2 拦截点 / 7.3 绕过

| 目标 | 方法 |
|---|---|
| 硬件指纹伪造 | 显示器 EDID 可改（虚拟显示器驱动）、MAC 可改（网卡高级属性/驱动层）、DirectX 信息来自注册表可写 → 三者同时改才能骗过交叉校验 |
| 阻止上报 | WinHTTP 走 `winhttp.dll`：在进程内 hook `WinHttpSendRequest` 即可截获/篡改；或让 DNS 解析失败（hosts） |
| 让签名失效 | `CryptSignHashW` 用容器里的私钥 → 容器在 `%APPDATA%\Microsoft\Crypto\` 下，删除后它必须重建（新指纹） |

## 8. `ACE-SSC64.dll`

### 8.1 干什么

| 证据 | 含义 |
|---|---|
| `CryptCATAdminAcquireContext` / `CryptCATAdminCalcHashFromFileHandle` / `CryptCATAdminEnumCatalogFromHash` | **目录签名校验**：判断文件是否被微软 WHQL 目录签名（用于放行系统文件） |
| `SOFTWARE\Khronos\OpenCL\Vendors` / `SOFTWARE\Khronos\Vulkan\Drivers` | 枚举 GPU 计算驱动（OpenCL/Vulkan）→ 检测 GPU 挖矿/作弊 |
| `\\.\%C:` / `\\.\%s` | 原始卷访问 |
| `CryptEncrypt` / `CryptImportKey` | 通信加密 |
| `WinHTTP` + `WSAIoctl` | 上报与网络探测 |

### 8.2 拦截点 / 8.3 绕过

| 目标 | 方法 |
|---|---|
| 让非签名文件被当系统文件放行 | 目录校验查的是**系统目录库**（`%SystemRoot%\System32\CatRoot\`）→ 把自己的文件的哈希加进某个 `.cat`？不可行（cat 有签名）。真正可行的是**替换校验函数的返回值**（用户态 patch `CryptCATAdminEnumCatalogFromHash`） |
| 隐藏 GPU 计算 | 删除/重命名 `Khronos\OpenCL\Vendors` 键值可让它以为无 GPU 计算环境，但 `ACE-CORE` 会用 PCI 交叉验证 → 需同时改 PCI 上报 |
| 绕过卷直读 | 它读的是卷的原始扇区 → 数据放在文件系统**上层**（NTFS 压缩/加密）时它读到的是密文，天然不可读 |

## 9. `ACE-ATS64.dll`

### 9.1 干什么

| 证据 | 含义 |
|---|---|
| `NtMapViewOfSection` / `NtCreateSection` / `NtUnmapViewOfSection` | 映射目标进程内存 → **内存扫描** |
| `NtQueryVirtualMemory` / `NtQuerySystemInformation` | 枚举区域、进程 |
| `WinHTTP`(10) + `WS2_32`(9) | 上报 |
| `CRYPT32`(8) | 签名/哈希 |
| `RtlVirtualUnwind` / `RtlLookupFunctionEntry` | 栈回溯（判定调用来源） |

### 9.2 拦截点 / 9.3 绕过

| 目标 | 方法 |
|---|---|
| 躲内存扫描 | 扫描读的是 `MEM_IMAGE`/`MEM_PRIVATE` 的**已提交页** → 把敏感数据放在 `MEM_MAPPED` 的文件映射里（扫描器常跳过）、或用 `PAGE_GUARD` + 单次解密 |
| 干扰栈回溯 | 它用 `RtlVirtualUnwind` 展开 → 破坏 `.pdata` 或让关键函数无 unwind 信息（手写汇编 + 自建 SEH） |
| 阻断映射 | `NtMapViewOfSection` 需要 `PROCESS_VM_READ` → 目标进程设 `PROCESS_PROTECTION`（`PsProtectedProcess`）可拒绝 |

# 三、跨组件攻击面

| 面 | 证据 | 绕过/利用 |
|---|---|---|
| **共享互斥体** | `Global\Ver`（Service64/Tray）、`Global\77775BF5-…`（SGuard64/Update64） | 预先占位使其单实例逻辑失效；互斥体句柄可被 `NtQueryMutant` 枚举 |
| **固定命名管道** | `\\.\pipe\ebda72a0-…-%d`、`\\.\pipe\` | 可枚举、可连接（受 ACL）、可抢先创建 |
| **明文 HTTP 下载** | `http://%s/d?dn=%s`（ACE-Safe） | DNS/hosts 劫持可读可改下发清单 |
| **BAM 执行历史** | `Services\bam\State\UserSettings\{SID}` | 删除值即清除"谁运行过什么" |
| **目录签名放行** | `CryptCATAdmin*`（ACE-SSC64） | 系统目录库是唯一可信源，patch 校验函数是最短路径 |
| **GPU 厂商键** | `SOFTWARE\Khronos\OpenCL\Vendors`、`Vulkan\Drivers` | 可删可改，但与 PCI 交叉验证冲突 |
| **驱动设备名** | `ACE-SSC-DRV64`、`ACE-BOOT` 明文；`ACE-BASE` 混淆 GUID | 明文者优先攻击 |
| **日志** | `ace-boot-*.log` 加密（密钥在 `.tvm0`） | 不能解密 → 但可**改名/截断**制造盲区 |

# 四、绕过方法总表（按目标）

| 想达到的效果 | 首选手段 | 代价 | 被谁挡 |
|---|---|---|---|
| 不被反调试发现 | 硬件断点 + 不调用 `DebugActiveProcess`；或 ETW 侧信道 | 低 | `ACE-BASE` 的 `NtQueryInformationThread` 检查 `DebugPort` |
| 隐藏进程 | 过滤 `SystemProcessInformation` 返回缓冲 | 中 | `ACE-CSI64` 与内核枚举交叉验证 |
| 隐藏内存内容 | `PAGE_GUARD` + 按需解密；敏感数据放文件映射 | 中 | `ACE-ATS64` 的 `NtMapViewOfSection` 扫描 |
| 绕过文件校验 | 硬链接/挂载点让路径失真；或改分区尾部 | 中 | `ACE-BOOT` 的裸磁盘读 |
| 绕过网络拦截 | 更高权重的 WFP 过滤器；或用 NDIS 协议驱动 | 高 | `ACE-CORE` 的 WFP + NDIS 双挂 |
| 阻断上报 | hook `WinHttp*`；hosts 指向本地 | 低 | `ACE-Service64` 的长连接重试 |
| 阻止自启/守护 | 预占全局互斥体；给 Run 键设 ACL | 低 | 服务守护重启 |
| 清除痕迹 | 删 BAM 值、清事件日志、改名日志文件 | 低 | `ACE-BOOT` 日志（加密但可见） |
| 反检测硬件 | 改 EDID/MAC/DMI + hypervisor 隐藏 | 高 | `ACE-DFS64` 的三路交叉校验 |

# 五、防守方视角（如果要加固这套东西）

| 现弱点 | 加固方向 |
|---|---|
| `ACE-Safe` 明文 HTTP | 全链路 TLS + 证书固定 |
| `ACE-SSC-DRV64` 设备名明文、无保护段 | 设备名混淆 + `.tvm0` 保护 + SDDL 收紧 |
| `ACE-SSC64` 依赖用户态校验函数 | 校验下沉到内核（`CiVerifyHashInCatalog`） |
| `ACE-BASE` 无 minifilter 注册 | 注册真正的 minifilter 而非仅查路径 |
| 共享互斥体可预占 | 用随机 GUID + 内核对象（`ZwCreateMutant` 在驱动侧） |
| 日志密钥在驱动内 | 用 DPAPI/TPM 保护密钥，密钥与机器绑定 |
| `ACE-Trace` 字符串混淆可还原 | 用编译期加密 + 运行时解密 |
