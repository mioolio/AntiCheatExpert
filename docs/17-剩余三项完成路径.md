# 17 · 剩余三项的完成路径（含负结果与方法）

本文记录三项尚未闭环的工作：日志解密、四个驱动的 IOCTL 码表、`ACE-DRV64` 载荷解包。
每一项都给出**已经排除的假设**、**为什么卡住**、以及**下一步的具体操作**（可直接执行）。

## 1. 日志解密

### 1.1 已确认

| 事实 | 证据 |
|---|---|
| 加密，非压缩 | 熵 7.96；zlib/lzma 在 0/8/16/24/32 偏移全部失败 |
| 非 ECB | 65,265 个 16 字节块无重复 |
| 非固定周期 XOR | 周期 16/32/64/256 自相关 0.004–0.006 |
| **密钥固定** | 11-18 与 11-21 的日志共享 24 字节密文前缀 |
| 写盘处无变换 | `ZwWriteFile` 前只是把缓冲按长度写出（`0x450FE` 处助手） |
| 加密在记录构造阶段 | `0x40B0` 格式化路径 → `0x43B0` 格式化 → `0x44C60` 开文件 → `0x486D0` 上下文（池标签 `'jacy'`） |
| 日志条目管线 | `0x1E40`（追加）：加锁 → `0x48140` → `0x47500` 取时间 → 清 0x1FC 栈缓冲 → `0x48C30` 格式化 → `0x3A40` 入队 |
| 文件头结构 | `0x48AE4` 处写 `magic 0x013525DD`、长度 `0x118`、标志 `0x01000800`，随后以 `xmm` 循环拷贝 0x80 字节 |

### 1.2 已排除的密钥（共 16,535 个候选）

| 轮次 | 候选 | 组合 | 最佳可打印率 |
|---|---|---|---|
| 1 | 19 个关键词的 md5/sha1/sha256/原文 + `.rdata`/`.data` 的 16/32 字节高熵窗口（各 2,000）+ `.dat` 中段 | 3,007 | 0.51 |
| 2 | 同上，另加密文起点 0/16/24/32（应对"24 字节是明文头"） | 13,528 | 0.52 |

正确密钥应 > 0.9。另：日志中**没有** `0x013525DD`、`0x01343BEB`、`0x01000800` 任何一个魔数（明文头也被加密）。

### 1.3 为什么卡住

密钥/IV 不在明文常量、不在注册表、不在 `.dat` 明文中段；只能来自 `.tvm0`（1.5 MB）内的 KDF，或由机器相关量派生。

### 1.4 下一步（二选一）

**A. 动态（最快，10 分钟）**

```
kd> bp 0x140001E40                       ; 日志追加
kd> bp 0x1400486D0                       ; 日志上下文（结构里应含 key/iv）
kd> bp 0x140048AE4                       ; 文件头构造（magic 0x013525DD）
```
在 `0x48AE4` 命中后 `dq rbp+0x100 L20`，把上下文里的 0x80 字节抄下来，即为候选密钥块；
再用 `tools/log_crypt.py` 里现成的 `rc4` / `chacha20` 试算，比对 `0x013525DD` 是否出现在明文头部。

**B. 静态（1–3 天）**

在 `0x1E40 → 0x48C30 → 0x3A40` 链上寻找对缓冲的按字节变换；若变换在 `.tvm0`，用
`python tools\trace_any.py ACE-BOOT.sys <rva>` 折叠控制流后取密钥常量。

## 2. 四个驱动的 IOCTL 码表

### 2.1 已确认

| 驱动 | 设备名 | 入口 |
|---|---|---|
| `ACE-BASE.sys` | `\Device\ACE-BASE` + 混淆 GUID `{TF9AC12E-…}` | `0x3E330` → `jmp 0x465C8B`（`.tvm0`）→ 寄存器搬运 → `call .tvm0+0x110F74` |
| `ACE-BOOT.sys` | `\Device\ACE-BOOT` | 未定位 |
| `ACE-CORE302706.sys` | 密文 | 未定位 |
| `ACE-SSC-DRV64.sys` | `\Device\ACE-SSC-DRV64` | 未定位 |

### 2.2 负结果

| 假设 | 方法 | 结果 |
|---|---|---|
| 控制码以 `cmp r32, imm32` 立即数出现 | `tools/sys_ioctl.py`（按 DEVICE_TYPE ∈ {0x22, 0x8000..} 过滤） | 只命中 `0x80000000`/`0x80000005` 等符号位常量，非控制码 |
| 存在 `{code, handler}` 静态表（12/16 字节步长） | `tools/ioctl_table.py` | 四个驱动全部 0 命中 |
| `IoValidateDeviceIoControlAccess` 可作锚点 | `tools/iat_refs.py` | 该函数**不在导入表**，是字符串表里动态解析的 |

### 2.3 为什么卡住

派发既不在立即数、也不在静态表，只可能在 `.tvm0` 里用"计算跳转 + 掩码比较"实现（与 `ACE-ADVT` 的 `0x9C51BBD3` 掩码同理）。

### 2.4 下一步

```
kd> bp 0x1400465C8B                  ; ACE-BASE 的 DEVICE_CONTROL 入口
kd> bp 0x14004A8F74                  ; 其真实逻辑（.tvm0+0x110F74）
kd> bp nt!IoValidateDeviceIoControlAccess
```
命中后看 `[Irp+0xB8]+0x18`（`IoControlCode`）与 `rcx/rdx` 的取值，连续发 3–5 个不同控制码即可把码表对上。

静态路线：`trace_any.py ACE-BASE.sys 0x4A8F74 2000` 未能在 400 条内收敛（保护器在此处用了与 ADVT 不同的跳板形态），需要先扩展折叠器识别模式。

## 3. `ACE-DRV64.dll` 载荷解包

### 3.1 结构

```
.text      va=0x001000  vsize=0x4D4144  raw=0        ← 无文件数据
.;9C       va=0x797000  vsize=0xAAC161  raw=0        ← 无文件数据
.A;6       va=0x1246000 vsize=0x17E519C raw=0x17E5200  ← 25 MB 实体，可执行+可写
.rsrc      va=0x2A2D000 vsize=0x89F498  raw=0x800
```

笔误更正：`.A;6` 的 `chars = 0x68000060`（含 `MEM_WRITE`），是**自解压/自修改**载荷的典型特征。

### 3.2 已完成

字节保真重建达成（`differing_bytes = 0`），因为该文件按数据转录。

### 3.3 下一步

1. 找入口：EFI 应用的 `_ModuleEntryPoint` 在 `.text`（`raw=0`，运行时由载荷填充）——需要先弄清 `.A;6` 的头部格式；
2. 静态：`.A;6` 起始 0x100 字节做熵/结构分析，寻找长度+偏移字段（`ace-boot.dat` 就是这种 4 dword 头部）；
3. 动态：在 UEFI 环境（OVMF/VMware）加载后 dump 内存，或在内核侧 hook `MiMapViewOfSection` 抓解包后的镜像。
